# 文档编写规范

[English](docs-checklist.md) | **简体中文**

新增或修改文档前先确定读者和任务，再选择位置。环境安装、预览、构建和发布命令见
[站点维护指南（英文）](../developers/documentation.md)。

## 1. 按读者和用途归类

| 用途 | 新文档位置 | 应包含什么 |
| --- | --- | --- |
| 普通用户完成具体任务 | `docs/user-guide/` | 目标、前提、操作、可见结果、失败恢复、下一步 |
| 插件作者学习开发 | `docs/developers/` | 目标、可运行示例、验证方式、下一课、接口参考 |
| 开发者查阅技术契约 | `docs/reference/` | 适用范围、职责归属、契约、限制、相关参考 |
| 宿主与文档贡献者 | `docs/contributing/` | 工作流程、检查命令、预期结果、后续步骤 |
| 方案、诊断或验收记录 | `docs/internal/` 下的 `design/`、`plans/`、`performance/`、`validation/` | 日期或版本、状态、证据、尚未验证的范围 |

已发布的根目录技术文档保持原路径，避免破坏已有链接；新技术参考放到 `reference/`。
插件专属说明留在插件目录，由学习指南链接过去。仓库 README 是入口，不重复整本手册。
历史记录不进入网站和应用内手册；其中的测试数字只说明当时的验证结果。

## 2. 每页只使用一种正文语言

- 英文主文档使用 `topic.md`，中文使用同目录的 `topic.zh-CN.md`，不要在同一页拼接两种正文。
- 两个版本都存在时，在页首互相链接。只有中文版的示例可以独立存在，但必须带语言后缀并加入中文导航。
- 命令、API 标识符和准确的界面名称保持原样，用当前页面的语言解释。
- 中文页链接到尚无译文的页面时，明确标注“英文”。不要把不完整译文描述为完整指南。
- 行为变更时同步两种版本；无法同步完整内容时，说明中文页覆盖的范围并指向维护中的英文主文档。
  自动检查只能发现语言混排，不能判断译文是否准确，仍需人工审阅。

## 3. 让读者知道从哪里开始、接下来做什么

每页只有一个一级标题 `#`，然后依次使用 `##`、`###`，不要跳级。
开头交代读者和目标，步骤前列出前提，命令后说明预期结果，结尾链接具体的下一步。
教程负责带着做，操作指南负责完成任务，参考文档负责说明契约；通过链接衔接，避免重复大段内容。

## 4. 链接与示例必须可移植

- 页面和图片使用相对链接，文件名大小写必须准确；Windows 能找到的路径不一定能通过 Linux CI。
- 源码使用仓库相对链接，网站构建时会转换为 GitHub 链接，离线手册会标为在线资源。
- 不要链接 `.tmp/`、`.outputs/` 等忽略目录中的本机产物。历史记录可用行内代码记录路径，
  需要公开展示的图片或数据应放入合适的受版本控制目录。
- 代码块标明语言和运行目录；PowerShell 与 shell 语法不通用时分别说明。
- 使用离线阅读器也能呈现的标准 Markdown，首页之外不依赖站点专属 HTML 布局。

## 5. 注册与验证

公开页面必须加入 `mkdocs.yml` 的对应读者栏目，中文页进入中文栏目。
`internal/` 和素材目录的 README 整体排除；不要通过新增单页排除来掩盖未完成的公开文档。

在仓库根目录，用文档虚拟环境的 Python 运行与 CI 相同的入口：

```sh
python scripts/docs.py check
```

检查包含页面清单、标题层级、语言分离、仓库链接、严格构建、生成页面的链接与锚点、资源和搜索范围。
涉及应用内手册或页面清单时，还要运行[维护指南（英文）](../developers/documentation.md#in-app-offline-manual)
中的 Help 测试和前端构建。样式变更需检查明暗主题、桌面与手机宽度。
PR 说明受益读者、实际改动和已运行的检查；本地构建通过不等于 GitHub Pages 已部署成功。
