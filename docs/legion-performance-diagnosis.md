# Legion 实例化与密集画布性能排查

2026-09-25。对应场景：保存 MatCreator 为 Legion 预设后，从牌组拖回画布；卡片密集时平移、缩放卡顿。

本文先保留优化前的诊断记录，文末记录随后完成的正式优化和验证。测量使用独立数据目录、Python 性能分析及 Chrome 实际拖放；数字来自本机开发环境，不是生产构建或所有硬件的性能保证。第 1–4 节的“当前实现”均指优化前代码。

真实复现“保存 MatCreator → 放入牌组 → 鼠标拖入画布”后，从释放鼠标到根卡片可见并经过下一帧共 **3.413 秒**，其中实例化 API 约 **2.821 秒**，响应后至测量到可见帧约 **0.568 秒**。该测量通过真实 pointer 拖放完成，不是单独调用创建接口。后者包含浏览器渲染、自动化可见性检查和下一帧等待，不应全部视为纯绘制耗时。

## 1. 保存后的 MatCreator：大文档反复重写是主要瓶颈

内置 MatCreator 的蓝图有 10 个节点，但知识集合还会生成 42 个 Skill 成员，实际产生 52 个节点。保存后，蓝图包含全部 52 个节点，本次蓝图大小为 1,829,265 字节。

保存后的实例化对每个 Skill 先初始化默认文档，再恢复保存的文档：

- `backend/services.py:866`：`_create_card()` 写入默认文档。
- `backend/services.py:2032`：实例化再写入 `initial_document`。
- `backend/node_documents.py:53`：每次写成员文档都会调用 `touch_parent()`。
- `backend/node_containers.py:10`：所谓刷新父文档实际是读取、解析并重新写入完整文档；不是只递增版本号。

本次知识集合的父文档为 **1,102,383 个字符**。恢复 42 个成员触发 **84 次父文档刷新**，重复执行大 JSON 的解析、序列化和 SQLite 写入。

| 后端服务层测量，启用 cProfile | 耗时 |
| --- | ---: |
| 保存后实例化 52 个节点，当前实现 | 3.296 秒 |
| 其中 `touch_parent` 累计耗时 | 2.488 秒 |
| 诊断实验：同一父文档的刷新合并到最后一次 | 1.215 / 1.202 秒 |
| 内置 MatCreator 当前实现 | 1.270 秒 |
| 内置 MatCreator 合并父文档刷新实验 | 0.458 / 0.439 秒 |

保存后路径的分析还观察到 556 次 SQLite commit。瓶颈不是简单的“52 张卡太多”，而是成员创建引发的大文档重复写入。原始内置预设的浏览器测量为 API 约 1.34–1.53 秒，实例化调用至根节点显示约 1.56–1.81 秒；这些数字不能替代保存后拖放路径的测量。

诊断实验只在独立进程里临时合并 `touch_parent`，用于验证耗时归因。它改变了中间版本递增和通知次数，不能直接当成已完成的产品修复。正式实现应明确批量导入的版本与事件语义，并避免恢复文档前的冗余默认文档写入。

## 2. 为什么拖放后像没有反应

`frontend/src/state/worldStore.ts:1046` 的实例化进入共享历史操作队列，再等待整个创建请求；`1073` 的 `await worldApi.instantiateLegion(...)` 返回后才合并返回节点。后端同样在整组创建成功后发布蓝图节点事件。集合派生成员另有事件路径，不能将其误认为已经有完整的分阶段部署反馈。

当前没有与落点绑定的部署占位卡或进度展示。较长的后端工作、排队以及后续挂载，会表现为卡片先消失、等待、最后出现。延迟反馈不是后端慢的起因，但放大了“没反应”的感受。

包含 Sandbox 的冷启动另有独立成本：`configure_options()` 调用 `registry.select()`，首次会发现运行时并等待可用性和联网能力探测，即使保存的是禁用联网。本机 coding 预设首次约 0.503 秒、缓存后约 0.025 秒。代码存在 15 秒运行时探测和 20 秒联网探测的超时边界；不能把这些上限当作本次实际发生的延迟。本次保存后 MatCreator 的主要已测瓶颈仍是文档重写。

## 3. 密集画布平移：浏览器绘制和图层处理是主要成本

独立 Chrome、Vite 开发构建、1600×1000、250 张普通 Text 卡，保留真实卡片组件和连接手柄，不使用会省略交互表面的 ephemeral 压力卡。场景约有 1.67 万个 DOM 元素。平移测试验证了 viewport 确实发生位移。

一次 80 步平移的追踪结果：

| 项目 | 累计时间 |
| --- | ---: |
| JavaScript | 约 0.331 秒 |
| Paint，合并同名嵌套区间后 | 约 1.753 秒 |
| Layerize | 约 1.518 秒 |
| HitTest | 约 0.762 秒 |

各类追踪事件可能互相包含，不能把表中数字直接相加。重绘样本覆盖整个 `#oaw-world-map`。这解释了为何只优化 React 计算或后台 terrain worker 不能解决平移卡顿。

另一轮相同 250 卡场景，临时 CSS 对照测得：

| 诊断条件 | 帧间隔 P95 |
| --- | ---: |
| 原始样式 | 100.1 ms |
| 关闭全局 backdrop-filter | 49.9 ms |
| viewport 增加 will-change: transform | 33.3 ms |
| 卡片节点增加 will-change: transform | 16.9 ms |

这些是单机、固定顺序的方向性实验，图层缓存、热身及系统负载会影响结果，不能解读为稳定的收益比例。它们支持进一步做卡片图层复用和背景模糊范围优化；没有据此直接给所有卡片永久提升图层。正式实现还要检查显存、缩放清晰度、文字和连接手柄显示，尤其是高倍率和大卡片。

React Flow 已开启 `onlyRenderVisibleElements`。问题并非完全没有视口裁剪：同屏密集的卡片仍需绘制完整表面；`chunks.ts` 还会把相交容器的所有后代加入候选集合。当前还没有按缩放倍率自动切换的轻量卡片表面。缩放路径的卡片几何和图层变化需要在修复时另做连续缩放验证；本次量化的交互主要是平移。

## 4. 编辑和事件更新：另有全局订阅放大问题

`frontend/src/effects/useNodeActivity.ts:7` 中每张卡片都订阅整个 `cards` 和 `events` 数组。即使不聚合成员状态，单卡片也会因其他卡片变化重新渲染，外层 `memo` 无法拦住组件自身的 store 订阅。

最终匹配的对照保持两侧均为 250 张已挂载卡片，连续 20 次仅修改一张卡片的名称：

| 测量 | 当前订阅 | 仅实验性缩小非聚合卡片的 cards 订阅 |
| --- | ---: | ---: |
| `useNodeActivity` 实际调用次数 | 5,020 | 20 |
| 累计 JavaScript 时间 | 4.250 秒 | 0.907 秒 |
| 帧间隔 P95 | 249.9 ms | 50.1 ms |

对照通过浏览器拦截模块响应完成，磁盘中的产品代码未改动。事件订阅仍保持原样，因此不代表运行时事件路径已优化。平移期间该 Hook 调用为 0，也说明它不是本次纯平移卡顿的直接主因。

次要放大点包括 `EquipmentToggle` 对全量卡片的计数扫描，以及 `WorldCanvas` 中按每个装备或 Agent 重复过滤数组。应先按 owner 建索引、缩小订阅，再看是否需要进一步优化；不能仅凭循环形态宣称它们占用了本次大部分时间。

## 诊断阶段建议的修改顺序

1. **保存后实例化**：合并集合父文档刷新；恢复文档时跳过冗余默认文档写入。明确批量写入的版本、事件和失败恢复语义。
2. **密集平移与缩放**：验证按显示尺寸与交互状态启用的图层复用，控制 backdrop-filter 范围；必要时增加缩小时的轻量卡片表面。
3. **即时反馈**：拖放落点显示部署占位和失败状态，让等待可见。
4. **更新局部化**：单卡状态与事件按 ID 订阅，容器聚合使用成员索引，消除无关卡片的重渲染。

## 正式优化（2026-09-25）

### 实现

1. **父文档只递增版本。** `StateStore.touch()` 在事务中更新版本和时间戳列，不读取、解析、重新序列化原 JSON。`touch_parent()` 使用这一操作，缺少持久化文档的旧容器仍走显式初始化。权限、乐观并发校验、scope 版本和每次更新事件均保留；保存后 MatCreator 仍有 84 次父文档失效通知。正式实现没有采用诊断用的“合并为一次通知”，也没有跳过插件初始化生命周期。
2. **落点即时反馈。** 在进入历史操作队列之前记录临时部署标记，显示“等待部署”或“正在部署”。标记固定在手势落点，平移和缩放不会改变部署位置；成功、失败、校验不通过都会清理。标记独立于世界节点和撤销栈，支持中英文及减少动画设置。
3. **限定范围的卡片图层缓存。** 总览缩放 `zoom <= 0.75` 时，为不超过 `360 × 420` 的 node/preview 表面启用 `will-change: transform`。最多缓存当前主画布前 512 个已挂载节点中的合格表面；更多节点仍正常显示。放大后释放提示，大型编辑器、Glue 表面和嵌套画布不适用。平移时不修改 DOM 属性，也不触发该控制组件的 React 渲染。
4. **活动状态订阅局部化。** 卡片只在实际展示的活动状态改变时重渲染；无关卡片编辑及无关运行事件不会刷新所有卡片。容器成员状态与终态事件仍会更新聚合状态。非 Agent 卡片不再扫描装备计数，装备关闭操作在点击时读取最新数据。

### 正式代码测量与边界

重新启动独立浏览器，复现真实“保存 MatCreator → 放入牌组 → 鼠标拖回画布”，得到：

| 从释放鼠标开始计时 | 优化前 | 正式版 |
| --- | ---: | ---: |
| 根卡片可见并经过下一帧 | 3.413 秒 | 1.949 秒 |
| 实例化 API | 2.821 秒 | 1.075 秒 |
| 响应后至测量到可见帧 | 0.568 秒 | 0.824 秒 |

本次端到端样本约缩短 43%，主要来自后端；响应后的挂载与自动化可见性检查仍有成本。部署提示在等待期间可见，不需要等根卡片挂载才反馈。一次复测的开发代理 `/api/application` 出现本地连接超时，重新启动独立测试进程后完成测量；没有把启动失败计入拖放时间，也没有把这次单样本当作固定延迟保证。

后端使用相同的已保存 MatCreator（52 节点、1,829,265 字节蓝图）、cProfile，以及同一进程交错执行“旧、新、新、旧”。旧版从 Git HEAD 加载原 `touch_parent()`，其余服务代码与数据目录保持相同，禁用外部 Sandbox 运行时以隔离文档恢复成本：

| 顺序 | 父文档处理 | 实例化耗时 | 父文档通知 |
| --- | --- | ---: | ---: |
| 1 | 原版读写完整 JSON | 4.359 秒 | 84 |
| 2 | 正式版仅更新版本列 | 1.900 秒 | 84 |
| 3 | 正式版仅更新版本列 | 1.913 秒 | 84 |
| 4 | 原版读写完整 JSON | 7.059 秒 | 84 |

这组对照中正式版耗时低约 56%–73%。各次创建会累积世界节点，且机器负载明显波动，所以不用这个百分比作固定性能承诺。早些时候正式版单次测得 0.629 秒，后续独立三次为 1.416/2.135/2.193 秒；完整保留这些结果，避免只报告最快样本。这里是服务层计时，不能当作鼠标释放到画布显示的总时间。

密集画布继续使用 250 张普通 Text 卡、1600×1000、实际 250 张挂载卡片：

| 项目 | 优化前诊断 | 正式版三轮复测 |
| --- | ---: | ---: |
| 平移帧间隔 P95 | 100.1 ms | 66.7 / 66.4 / 50.1 ms |
| 连续 20 次改单卡时的活动 Hook 调用 | 5,020 | 每轮均为 20 |
| 上述改单卡累计 JavaScript | 4.250 秒 | 1.284 / 1.179 / 1.188 秒 |
| 连续缩放帧间隔 P95 | 未保留同条件基线 | 83.4 / 83.4 / 116.5 ms |

另一次负载更高的同场景复核中，正式缓存平移 P95 为 149.9 ms，临时关闭缓存为 216.5/166.7 ms；对应主线程 TaskDuration 为 7.145 秒与 12.458/11.075 秒。增加 viewport 缓存或给所有节点加提示都没有明显好于当前受限策略，因此未扩大缓存范围。该对照最后一个空 CSS 样式注入步骤被 Playwright 拒绝，前面的测量已完成并保存，不能将这轮称为完整通过的测试。

**没有达到稳定 60 FPS。** 这些数据支持减少重复绘制与无关渲染，但连续缩放、很多大型展开卡片仍可能卡顿。此轮没有引入缩放级别自动简化内容，没有测得显存占用的跨设备上限，也没有用图层提示替代现有视口裁剪。旧诊断中的 16.9 ms 最佳样本不作为正式版交付指标。
